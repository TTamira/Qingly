# 青序｜完整产品与技术架构

> 设计方向：低饱和薰衣草紫、淡丁香紫与雾灰色搭配，清爽、柔和、有层次，避免大面积纯白或单调灰绿色。

---

## 一、产品定位与核心原则

青序是一款个人生活与工作管理工作台，帮助用户管理目标、计划、学习、复盘和私人生活，并通过多设备同步维持连续性。

**核心原则：**

- **本地优先**：日常操作尽可能在本机完成，断网仍可使用。
- **数据分区**：工作空间、私人空间、本地资料拥有不同的数据访问与同步策略。
- **按设备授权**：不同设备可以获得不同的数据访问权限。
- **隐私优先**：私人数据客户端加密；工作电脑可以按需临时查看，但不默认获取私人数据。
- **渐进式开发**：先稳定数据模型与本地存储，再实现同步和移动端，不一次性重写全部功能。

## 二、整体技术架构

```
┌─────────────────────────────────────┐
│         应用表现层 UI               │
│   桌面端 / 手机端 / 平板端          │
│   页面、主题、导航、交互、响应式    │
├─────────────────────────────────────┤
│         业务与权限层                │
│   目标、任务、专注、日历、复盘      │
│   工作/私人/本地资料的访问控制      │
├─────────────────────────────────────┤
│      统一数据访问层 Store           │
│   数据校验、查询、更新、迁移        │
│   权限检查、业务逻辑不直接操作底层  │
├─────────────────────────────────────┤
│         本地数据层                  │
│   localStorage 起步                 │
│   按需迁移 IndexedDB                │
│   桌面端通过 Rust 提供安全存储      │
├─────────────────────────────────────┤
│        同步与加密层                 │
│   Tauri Rust 后端访问坚果云 WebDAV  │
│   负责加密、版本校验、冲突与恢复    │
└─────────────────────────────────────┘
```

### 技术选型

| 层级 | 当前方案 |
|------|---------|
| 前端 | HTML、CSS、JavaScript，现有单文件 workbench-desktop.html |
| 桌面容器 | Tauri 2.x、Rust、Windows WebView2 |
| 本地存储 | localStorage + Store 抽象层 |
| 远端同步 | 坚果云 WebDAV，由 Rust 后端发起请求 |
| 主题 | CSS 变量 + data-theme，共 8 套主题 |
| 移动端 | 评估 PWA 与 Tauri 移动端，不预先锁定方案 |
| 后续存储升级 | 按数据量、查询与可靠性需求评估 IndexedDB |

**重要约束**：不要让页面代码到处直接读写 `localStorage`，也不要让前端直接持有 WebDAV 密码。所有数据操作应经过统一接口，方便以后替换存储实现。

## 三、功能模块设计

### 1. 首页与今日状态
- 今日任务、进度与状态概览
- 快捷记录入口
- 今日专注时长与目标推进情况
- 工作与私人空间的独立视图

### 2. 目标与计划
- 总目标 → 阶段目标 → 周目标 → 每日任务
- 目标树、任务关联与进度统计
- 方向推进，记录每个长期方向的进展
- 支持调整、延期、暂停和完成目标

### 3. 护眼专注
- 默认 45 分钟专注 + 15 分钟休息
- 专注与休息自动循环
- 支持暂停、继续、结束
- 记录专注历史与累计时长

### 4. 日历与记录
- 日历查看任务、目标节点与记录
- 快捷记录灵感碎片和临时事项
- 工作复盘与阶段总结
- 支持按日期、类型和空间检索

### 5. 本地资料
- 以阅读界面作为独立入口
- 记录本地文件与阅读进度
- **默认只保存在当前设备**
- **不进入常规导出、云同步或工作空间数据包**

> 以上模块是功能边界，不要求每个模块立即重写。现有功能先保留，通过统一 Store 和权限层逐步接入新架构。

## 四、三类数据分区

这是青序最关键的架构决定。不能只在界面上切换标签，而要在**数据访问层真正隔离**。

### A. 工作空间 — 可跨设备同步

工作任务、职业目标、学习计划、工作复盘、工作相关状态。

个人电脑、工作电脑、私人手机、私人平板均可授权访问。

### B. 私人空间 — 独立加密与授权

财务、身体与生活状态、关系记录、私人日记。

手机、私人平板、个人电脑可以同步；工作电脑可选择临时查看或经授权完整同步。

### C. 本地资料 — 仅本机

原始资料文件、阅读进度及相关本地记录。

不进入任何云同步或常规导出，独立于工作与私人数据分区。

### 数据层必须遵守的规则

- 每条记录都有明确的 `space` 或所属数据分区。
- 页面不能绕过权限层直接读取其他分区。
- 工作空间与私人空间使用**独立同步清单和数据包**，不能打成一个全量包。
- 本地资料不注册到云同步队列，也不能因为全量导出而被意外带出。
- 切换工作/私人空间时，不只是隐藏卡片，还要**限制查询、写入、搜索、导出和同步范围**。
- 迁移旧数据时，先识别、备份和验证归属；无法确定的数据不能静默归入某个空间。

## 五、设备权限与私人空间安全

### 设备权限矩阵

| 设备 | 工作数据 | 私人数据 | 本地资料 |
|------|---------|---------|---------|
| 个人电脑 | 同步 | 同步、解锁 | 本机 |
| 工作电脑 | 同步 | 默认关闭，可临时查看或完整授权 | 本机 |
| 私人手机 | 同步 | 同步、解锁 | 本机 |
| 私人平板 | 同步 | 同步、解锁 | 本机 |

设备名称只是默认策略。用户可以修改授权，但每台设备都必须独立记录授权状态。

### 私人空间的加密与解锁

- 私人空间使用**独立密码**，不等同于青序的登录密码。
- 使用经过验证的密码派生算法和成熟加密库；不能直接把密码当作加密密钥。
- 私人数据在客户端加密后再上传，远端只保存密文。
- 首次启用时提供恢复密钥或其他可靠恢复机制。忘记密码且没有恢复材料时，数据可能无法恢复。
- 支持手动锁定、闲置自动锁定和设备授权撤销。
- WebDAV 凭据、解密密钥**不得明文写入** HTML、普通配置文件或日志；桌面端应使用操作系统凭据安全存储能力。

### 工作电脑的两种私人空间模式

**临时查看模式（默认推荐）**

需要时输入私人空间密码并按需获取数据；不启用后台私人数据同步，不长期保存解密密钥，尽可能减少明文缓存。锁定后清理可控的临时数据。

**完整同步模式**

用户明确授权后，工作电脑可以保存私人数据的本地加密副本，并在解锁后使用。需要单独授权、可撤销，并提示本地备份、系统缓存和设备管理可能带来的风险。

> 需要明确：临时查看不能保证设备完全不留下私人信息。截图、系统级备份、崩溃转储或恶意软件等风险不能单靠应用锁定消除。

另外，私人数据即使只下载密文，也不符合"工作电脑默认不下载私人数据"的要求。因此工作电脑必须默认关闭私人数据下载，并且不能仅依赖 UI 隐藏或文件命名来隔离。若使用同一个 WebDAV 账号，必须验证其实际权限能力；不能假定坚果云一定支持所需的路径级访问控制。

## 六、多端同步架构

同步服务采用坚果云 WebDAV，但它不是数据库事务系统，因此需要在应用内部实现**版本管理、冲突检测和恢复机制**。

```
设备端数据（本地操作、离线读写、数据分区检查）
        ↓
同步协调器（授权校验 → 变更检测 → 版本比较 → 冲突处理 → 重试）
        ↓
┌─────────────┐  ┌─────────────┐
│  工作同步区  │  │  私人同步区  │
│  工作数据包  │  │  独立密文包  │
└─────────────┘  └─────────────┘
        ↓
本地资料不进入同步链路
```

### 同步数据模型

建议每条记录至少包含：

| 字段 | 用途 |
|------|------|
| id | 全局唯一记录标识 |
| space | 所属空间 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |
| version | 记录版本 |
| deletedAt | 删除标记，用于跨设备同步删除 |

同时建立设备标识、同步游标、数据模式版本 `schemaVersion`、远端文件版本或 ETag 等同步元数据。

### 必须实现的同步规则

- **离线可用**：断网期间记录变更，恢复网络后重试。
- **冲突可见**：两个设备修改同一记录时，保留双方版本，让用户选择或合并；不能静默覆盖。
- **安全写入**：先写临时文件，再校验内容，最后替换正式数据。
- **并发保护**：尽可能利用服务器提供的版本校验机制；若 WebDAV 服务端不支持可靠的条件写入，就不能假装已经实现原子并发控制。
- **删除可同步**：使用删除墓碑，等所有授权设备确认或达到可靠的清理条件后再清除。
- **备份可恢复**：保留可恢复的历史版本，验证备份完整性。
- **数据分区独立**：工作数据同步失败，不应破坏私人数据；私人空间未解锁时，不启动其解密或写入操作。
- **凭据安全**：WebDAV 密码与私人空间加密密钥分开管理。

> 需要特别注意：如果多人或多设备可能同时写入同一远端文件，仅靠"先下载、再上传"无法避免覆盖。实现时必须验证坚果云的实际 WebDAV 能力，并为并发冲突设计保守的处理方式。

## 七、本地存储与数据访问层

当前使用 `localStorage` 加 Store 抽象层，可以保留，但应先确认现有实现是否已具备完整的读写封装。

建议统一接口概念如下：

```js
store.get(space, id)
store.list(space, query)
store.create(space, record)
store.update(space, id, changes)
store.delete(space, id)
store.export(space, options)
```

> 这是接口示意，不代表要求立即改写现有代码。

### 存储策略

- **当前阶段**：保留 `localStorage`，先规范数据结构、权限和迁移。
- **后续阶段**：数据量、查询复杂度或可靠性要求超出当前能力时，再评估 IndexedDB。
- **私人空间**：本地存储与远端加密格式分开设计，不能将加密前的明文直接放入同步队列。
- **本地资料**：使用独立的本地存储路径和索引，避免被常规数据导出逻辑意外包含。
- **数据迁移**：每次结构变更都有版本号、迁移步骤、失败回滚与备份。

## 八、桌面端与移动端

### 桌面端

继续使用 Tauri 2.x + Rust + WebView2。

- 保留当前桌面布局与已有功能。
- 使用 `Alt+W` 切换工作与私人空间。
- 通过 Rust 后端执行 WebDAV 请求和必要的安全操作。
- 遵循 Tauri 最小权限原则，只开放确实需要的文件、网络和系统凭据访问能力。

### 手机端

底部五个入口：首页、计划、目标、复盘、我的。

单列卡片、快捷记录、醒目的专注计时器、可折叠目标树；私人空间解锁入口清晰可见。

### 平板端

左侧导航与多列布局，充分利用屏幕空间；支持键盘和触控操作。

移动端路线暂不直接定案：

- **PWA**：适合先验证移动布局、快捷操作与同步流程。
- **Tauri 移动端**：适合后续需要原生能力、更强本地文件访问或系统级安全存储的场景。

先评估现有单文件前端的兼容性、目标系统及必要原生能力，再决定最终方案。尤其要验证移动端的系统凭据存储、后台同步和本地文件访问能力，不能直接假定桌面端实现可以原样复用。

## 九、主题与视觉规范

当前 8 套主题继续保留，通过 CSS 变量与 `data-theme` 管理。

- **主推主题**：青序·紫。
- **基础色**：淡丁香紫、雾灰色。
- **辅助色**：灰青绿、豆沙粉等低饱和色。
- **状态色**：用于成功、提醒、错误等有语义的反馈。
- 页面需要层级与留白，避免所有卡片都是同一灰色。
- 同一主题下统一按钮、卡片、输入框、弹窗、导航和图标的视觉规则。
- 桌面、手机、平板共享设计变量，不要求完全相同的布局。

## 十、推荐开发路线

### Phase 1 — 基础稳定：数据模型与权限隔离

审查现有代码、统一 Store、规范记录结构和空间标记；实现工作/私人/本地资料的数据访问隔离，完成私人空间独立密码与加密设计。

### Phase 2 — 同步能力：坚果云 WebDAV

实现设备授权、独立数据分区、版本校验、冲突处理、离线重试、删除同步、备份与恢复。

### Phase 3 — 移动适配：手机与平板

先验证响应式布局和核心流程，再根据 PWA 与 Tauri 移动端的实测结果决定实现方式。

### Phase 4 — 按需升级：存储优化与体验完善

根据实际性能、查询需求和移动端兼容性决定是否迁移 IndexedDB；完善主题、检索、统计和数据维护工具。

## 十一、交给开发 AI 的硬性约束

### 技术现状
- 前端：单文件 HTML `workbench-desktop.html`。
- 桌面端：Tauri 2.x、Rust、Windows WebView2。
- 当前本地存储：localStorage + Store 抽象层。
- 云同步目标：坚果云 WebDAV，由 Rust 后端发起请求。
- 主题：8 套，通过 CSS 变量和 data-theme 管理。
- 移动端：尚未最终决定 PWA 或 Tauri 移动端。

### 三类数据分区
1. **工作空间**：工作任务、职业目标、学习计划、工作复盘、工作相关状态。
2. **私人空间**：财务、身体与生活状态、关系记录、私人日记。
3. **本地资料**：原始资料文件、阅读进度和本地记录，仅本机保存。

### 权限与同步
- 工作空间与私人空间必须在**数据访问层隔离**，不可只靠 UI 隐藏。
- 工作与私人数据必须使用**独立同步清单和数据包**。
- 本地资料**不进入同步队列和常规导出**。
- 私人空间使用**独立密码和客户端加密**，采用成熟、经过验证的密码学库。
- 工作电脑**默认不下载私人数据**、不保存长期私人解密密钥。
- 工作电脑支持用户主动授权的**临时查看模式**和可选**完整同步模式**。
- 临时查看模式应尽量减少本地持久化明文，但不能承诺绝对无痕。
- WebDAV 凭据和加密密钥**不得明文写入** HTML、普通配置文件或日志。
- 设备撤销、离线重试、并发冲突、删除墓碑、版本校验、备份恢复均须设计。
- **不允许冲突时静默覆盖**，不允许迁移失败后丢弃原数据。
- 必须验证坚果云真实支持的 WebDAV 权限和条件写入能力，**不得假设**其提供路径级权限或事务保证。
- Tauri 使用**最小权限原则**。
- 未经评估，**不得直接迁移 IndexedDB 或重写整个前端**。

### 开发顺序
1. 审查代码和现有数据格式，提交风险清单。
2. 提出数据模型、Store 接口、空间权限和迁移方案。
3. 先完成可验证的本地数据隔离和安全设计。
4. 实现同步协议与冲突恢复，并提供测试。
5. 再验证移动端方案。
6. 按需优化存储与视觉体验。

**每个阶段都要提供**：改动范围、文件清单、数据迁移方式、安全影响、测试结果、回滚方案。涉及私人数据或密钥的设计必须先解释风险，再实施；不得用伪加密、假权限或仅靠前端隐藏来代替真正的访问控制。

---

> **最终建议**：先做 Phase 1。在开始同步开发之前，先让开发 AI 检查现有代码与数据结构，确认工作、私人和本地资料的边界能够真正落实。否则越早加入多端同步，后续修复数据泄漏与迁移问题的成本就越高。
